# Руководство по проекту maxi_diagnostics

## Назначение

Это шаблон отдельной white-label системы школьной диагностики. Для каждой школы
предполагаются собственные репозиторий, Telegram-бот, домен, база данных, бренд,
учебные материалы и секреты. Пользователь проходит короткую или полную диагностику
в Telegram Mini App и получает рассчитанный на сервере результат прямо в
приложении. В Telegram приходит короткое сообщение со сводкой и кнопкой на экран
результата, а также запланированные напоминания. Сотрудники школы видят техническое состояние
диагностик и редактируют шаблоны сообщений через защищённую админку.

## Технологии и сервисы

- Backend: Python 3.11, FastAPI, aiogram, asyncpg, Pydantic, APScheduler.
  ReportLab и svglib остались только для проверки шрифтов и ресурсов школы.
- Frontend: Node.js 22, Next.js 16, React 19, TypeScript.
- Хранилище: PostgreSQL 16.
- Запуск: Docker Compose; пример production-прокси находится в
  `deploy/nginx/diagnostic.conf.example`.
- Сервисы Compose: `db`, `api`, `bot`, `miniapp`.

`api` обслуживает Mini App API, health check и админку. `bot` работает через long
polling, отправляет меню и результаты, а также раз в минуту запускает ограниченный
worker для доставки результатов и follow-up сообщений. `miniapp` — браузерный интерфейс прохождения
диагностики. PostgreSQL хранит прогресс, итоговые снимки, очередь доставок, шаблоны
сообщений и служебные состояния.

## Основной пользовательский поток

1. Telegram передаёт подписанный `initData`; backend проверяет подпись, время и
   пользователя.
2. `POST /bootstrap` возвращает публичный бренд, ссылки, каталог без правильных
   ответов, результаты и возобновляемую попытку.
3. Mini App сохраняет прогресс локально и через `POST /session/progress`. Ревизии
   прогресса и идентификатор сессии защищают от конфликтующих вкладок и устаревших
   записей.
4. `POST /session/complete` повторно валидирует ответы, считает результат только на
   сервере, сохраняет неизменяемый снимок результата и ставит доставку в очередь.
5. Worker отправляет в Telegram сводку результата с кнопкой на Mini App и
   обрабатывает отложенные уведомления с lease/retry-механикой.
6. `POST /session/viewed` и действия бота отмечают просмотр результата, чтобы
   ненужные напоминания были отменены.

## Карта репозитория

- `backend/diagnostic/api/` — FastAPI factory, публичные session endpoints,
  Telegram-аутентификация и модели запросов.
- `backend/diagnostic/bot/` — polling entrypoint, команды, обработчики и клавиатуры.
- `backend/diagnostic/admin/` — Basic-auth админка, HTML/JS и запросы для диагностики
  проблем доставки и удаления данных пользователя.
- `backend/diagnostic/db/` — пул asyncpg, идемпотентная схема, запросы попыток,
  уведомлений и шаблонов сообщений.
- `backend/diagnostic/catalog.py` — строгая модель каталога, исключение поля
  `correct` из публичной выдачи и версия контента.
- `backend/diagnostic/school.py` — загрузка бренда, ссылок и безопасных публичных
  ресурсов.
- `backend/diagnostic/scoring.py` — серверная проверка пяти типов вопросов и
  расчёт сильных/слабых тем.
- `backend/diagnostic/delivery.py`, `followups.py`, `worker.py` — доставка
  результата, напоминания и периодическая обработка очередей.
- `miniapp/app/` — клиентский интерфейс, API-клиент, типы, Telegram Web App adapter и
  восстановление локального прогресса.
- `school/` — заменяемая конфигурация конкретной школы: `brand.json`, `links.json`,
  `diagnostics/*.json`, `assets/`.
- `scripts/` — первичная инициализация школы, валидация контента, проверка брендовой
  изоляции, backup/restore и сбор лицензий.
- `tests/` — Python unit/integration/static tests; часть DB-тестов требует PostgreSQL.
- `docs/` — формат контента, deployment, operations и handoff.

## Контент школы

Формат полностью описан в `docs/CONTENT_FORMAT.md`. JSON-файлы читаются как строгий
UTF-8: запрещены дубли ключей, нестандартные числа и неизвестные поля. Поддерживаются
вопросы `single`, `multiple`, `matching`, числовой `input` и короткий
свободный `text`. Файлы и ресурсы имеют
жёсткие ограничения по размеру, количеству, путям и содержимому SVG/изображений.

После изменения `school/brand.json`, `school/links.json`, диагностик или ресурсов
обязательно выполнить:

```text
python scripts/validate_school.py
python scripts/check_brand_isolation.py
```

Обе команды должны завершиться сообщением `OK`. Перед публикацией истории репозитория
используется более строгая проверка `python scripts/check_brand_isolation.py --history`.

Каталог целиком собран из редакционно утверждённой выгрузки MAXIMUM (SharePoint)
скриптом `scripts/import_sharepoint_diagnostics.py`. Каждый вопрос имеет
идентификатор `sp-…`; других источников в `school/diagnostics/` нет. Скрипт
идемпотентен: повторный запуск заменяет ровно вопросы с этим префиксом и ресурсы
`assets/questions/sp-*` и обязан давать побайтово те же файлы. Он не трогает
`quick_count` и `full_count`. Полная диагностика — это первые `full_count`
вопросов файла, остальные пополняют банк тренажёра и дневного плана. Источники
без записи в плане импортируются первыми, поэтому префикс `full_count` остаётся
на тех же вопросах. Отчёт по каждому заданию, включая причину каждого пропуска, пишется в
`authoring/sharepoint-import/report.md`.

```text
python scripts/import_sharepoint_diagnostics.py <каталог-с-docx>
python scripts/import_sharepoint_diagnostics.py <каталог-с-docx> --plan <план.json>
```

Каталог источников должен содержать весь банк, включая 20 базовых DOCX. Скрипт
переписывает все вопросы `sp-` целиком, поэтому запуск на части выгрузки удалит
остальные. Необязательный `--plan` задаёт предмет, экзамен, сезон и тему для
перечисленных в нём файлов вместо разбора имени, сверяет каждый файл с
SHA-256 и добавляет в идентификатор слаг темы. Формат плана и решения по нему —
`authoring/sharepoint-inventory/phase-2-import-plan.json` и `PHASE_2.md`.

На вход идут только исходные редакционные DOCX MAXIMUM. Именно они совпадают с
`TRUSTED_SOURCE_HASHES`, и в репозитории их нет. `authoring/sharepoint-authoring/`
хранит те же документы, переписанные в авторский формат
`docs/AUTHORING_TEMPLATE.md`, и это другой формат: у него своя шапка и поле `Тип`
у каждого задания. Оба формата открывают задание абзацем `Задание N`, поэтому
раньше конвертер читал авторский документ, отбраковывал большую часть заданий как
`irregular_key` и заменял группу источника остатком. Теперь он читает шапку до
первого задания и останавливает весь запуск, называя файл. Тесты, которым нужен
редакционный исходник, берут каталог из `SHAREPOINT_SOURCE_DIR` со значением по
умолчанию `.tmp/sharepoint-sample` и пропускаются, если его нет.

Локальных каталогов источников два, и это легко упустить. `.tmp/sharepoint-sample`
плоско хранит 45 диагностик, чьё имя конвертер разбирает сам. `.tmp/lit-sample`
повторяет раскладку папок SharePoint и хранит 12 литературных тематических
пакетов, которым нужен `--plan
authoring/sharepoint-inventory/phase-2-literature-plan.json`: их имена конвертер
не разбирает, а слаг темы берётся из плана. Импортёр не ходит по подпапкам,
поэтому литературу перед запуском кладут в плоский каталог. Вместе эти два
набора воспроизводят все 402 вопроса каталога.

Дополнительные принимаемые формулировки короткого ответа перечисляются в
`authoring/answer-variants.json` по идентификатору вопроса. Скрипт читает этот
файл сам, поэтому формулировка, дописанная методистом, переживает перегенерацию
каталога. Правка `correct` прямо в `school/diagnostics/` не переживёт.
Идентификаторы проверяются на уникальность внутри каждого каталога, в том числе
в режиме `--dry-run`.

После импорта обязательны validation, brand isolation и Python-тесты. Не повышайте
лимиты каталога только ради полной исходной выгрузки: для этого потребуются
пагинация API, другая модель загрузки ресурсов и отдельный продуктовый контракт.

Часть заданий конвертируется в тип `text` (свободный краткий ответ). Он
поддержан в `catalog.py`, поэтому каталог проверяется обычной командой
`python scripts/validate_school.py`.

### Авторский формат документов

Формат, в котором приложение ничего не угадывает, описан в
`docs/AUTHORING_TEMPLATE.md`. Тип задания назван словом, пункты и варианты лежат
под своими заголовками, ответ стоит в своём поле. Читатель формата строгий: он
либо понимает документ целиком, либо называет задание и поле.

```text
python scripts/make_authoring_example.py <образец.docx>
python scripts/check_authoring_document.py <файл.docx>
python scripts/convert_to_authoring_template.py <исходный.docx> <результат.docx>
```

Перенос заполняет всё однозначное и помечает словом `ТРЕБУЕТ ПРОВЕРКИ` то, о чём
пришлось бы догадываться. Он же удаляет строки про запись ответа в бланк и
нумерует задания подряд, потому что авторский документ ведёт свою нумерацию.
Папка переводится целиком, с отчётом:

```text
python scripts/convert_to_authoring_template.py <папка> <папка> --report <отчёт.md>
```

Все 45 документов текущей выборки переведены в `authoring/sharepoint-authoring/`,
итоги по каждому — в `report.md` там же. Читатель не находит в них ни одного
расхождения с форматом: все 163 замечания это поля, которые заполняет методист.

Формат пока не подключён к сборке каталога. Импортёр редакционных документов
работает как прежде; переключение — отдельный шаг после того, как методист
заполнит первые документы.

### Карта источников SharePoint

Перед поиском или импортом учебных материалов прочитайте
`authoring/sharepoint-inventory/README.md`. Там указаны точка входа, коды
предметов, рабочие ветки ЕГЭ и правила выборочной загрузки. Количественный
срез архива ведётся в `authoring/sharepoint-inventory/PHASE_1.md`, итоги выборочной
загрузки, дубли и решения по импорту в `PHASE_2.md`.

Прежний каталог (178 вопросов из выгрузки Edcheck и 123 вопроса нашей кампании
`fipi-2026-min15`), конвертер Edcheck и методология авторской кампании лежат в
`authoring/archive/2026-09-pre-sharepoint/`. Этот каталог — справочный: его не
читают ни runtime, ни тесты, ни линтер.

## Критические инварианты

- Поле `correct` является строго серверным. Оно не должно попадать в TypeScript,
  HTML, bootstrap payload, публичные ресурсы или клиентские тестовые фикстуры.
- Не доверять Telegram user ID или данным профиля без проверки `initData`. Публичные
  session endpoints должны продолжать использовать общий dependency аутентификации.
- `APPLICATION_SECRET` должен быть уникальным и стабильным. Его изменение инвалидирует
  namespace браузерных сессий и версии контента активных попыток.
- Завершённый результат и повторный просмотр должны опираться на сохранённый
  `report_snapshot`, а не на текущий каталог школы.
- Сохранять optimistic revision/lease-проверки и идемпотентность запросов БД. У
  Telegram нет idempotency key, поэтому логика сверки message ID и ограниченных
  повторов защищает от большей части дублей.
- Для одного bot token одновременно запускается только одна polling-копия `bot`.
- Не логировать и не помещать в ошибки секреты, `initData`, необработанные ответы,
  персональные данные или полные payload. Ошибки доставки в БД намеренно
  редактируются и ограничиваются.
- Не ослаблять CORS, same-origin deployment, security headers, Basic auth админки и
  запрет публикации внутренних портов без отдельного security review.
- Соблюдать удаление данных и retention. После отправки или окончательного отказа
  чувствительные delivery-данные очищаются; удаление пользователя использует
  tombstone/session generation, чтобы старый клиент не восстановил запись.
- Схема находится в `backend/diagnostic/db/schema.py` и применяется идемпотентно.
  Любое изменение схемы должно сохранять существующие установки и иметь тест
  миграции/повторного запуска.
- `INSTALLATION_ID`, `IMAGE_NAMESPACE` и секреты не должны попадать в Git. `.env`
  остаётся локальным; все значения в `.env.example` должны быть пустыми или явно
  шаблонными.
- Сохранять существующий UTF-8 и кириллицу без перекодирования. Новые текстовые файлы
  создавать в UTF-8 без BOM.

## Где вносить изменения

- Новый тип или поле вопроса: синхронно обновить `catalog.py`, серверную проверку,
  API-валидацию, `miniapp/app/types.ts`, рендер и тесты; правильный ответ оставить
  только на backend.
- Изменение результата: проверить `scoring.py`, serialization в `api/sessions.py`,
  DB snapshot, бот и frontend types/UI.
- Изменение прогресса/завершения: учитывать конкурентные вкладки, revision conflict,
  supersede flow, повтор запроса и очистку локальной сессии.
- Изменение доставки: проверить точную lease-финализацию, отмену процесса,
  дедупликацию по message ID, удаление лишнего Telegram-сообщения и предел в
  восемь попыток.
- Изменение сообщений: использовать валидатор шаблонов и лимиты Telegram; учитывать
  HTML-экранирование и разрешённые placeholders.
- Изменение UI или бренда: учитывать build-time бренд в `miniapp/next.config.ts` и
  runtime бренд из `/bootstrap`; не хардкодить данные конкретной школы.
- Изменение эксплуатации: синхронно обновлять README, `docs/`, Compose/Nginx примеры
  и static tests, которые проверяют документированные команды.

## Локальная проверка

Python-зависимости устанавливаются из полного lock-файла, а не из списка прямых
зависимостей:

```text
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --no-deps -r requirements-dev-lock.txt
```

Для Python-тестов нужен `PYTHONPATH=backend`; DB-тесты используют
`TEST_DATABASE_URL`. Без него 79 тестов молча пропускаются, и поломка находится
только в CI после слияния. Одноразовая база поднимается двумя командами:

```text
docker run -d --name maxi-test-db -e POSTGRES_DB=diagnostic_test -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=local-test-password -p 55434:5432 postgres:16-alpine
$env:TEST_DATABASE_URL = "postgresql://postgres:local-test-password@127.0.0.1:55434/diagnostic_test"
```

С ней прогон даёт 930 passed и 1 skipped вместо 79 пропусков. Контейнер удаляется
через `docker rm -f maxi-test-db`. Имя заканчивается на `-test-db`, чужие
контейнеры трогать нельзя.

Полный CI-порядок:

```text
python scripts/validate_school.py
python scripts/check_brand_isolation.py --history
python -m ruff check backend scripts tests
python -m pytest -q
cd miniapp
npm ci
npm run test:unit
npm run typecheck
npm run build
npm test
cd ..
docker compose config --quiet
docker compose build
```

`npm test` дополнительно собирает production-версию и проверяет отрендеренный HTML.
При небольшой правке сначала запускайте узкий релевантный тест, затем все затронутые
гейты. Изменения контента всегда требуют двух проверок из раздела выше.

## Готовность изменения

Изменение считается готовым, когда соблюдены инварианты безопасности и приватности,
добавлены или обновлены тесты на изменённое поведение, проходят релевантные Python и
Mini App проверки, а изменения конфигурации/контента проходят validation и brand
isolation. Для deployment/DB/delivery-изменений дополнительно сверяйтесь с
`docs/DEPLOYMENT.md` и `docs/OPERATIONS.md`.
